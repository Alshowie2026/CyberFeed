# Data Model: User Authentication

## Persistence boundary

`simple-posts/data/auth.json` stores `{version:1,users:[],sessions:[],loginAttempts:[]}`; `posts.json` remains the existing array. Data files are outside `public/`. The server loads and validates both before accepting writes. A missing auth file means first-time initialization; malformed or unsupported data fails startup without overwriting it.

Each mutation prepares a new snapshot, writes a uniquely named same-directory temporary file with flush, closes it, then renames it over the target. Publish in-memory state and report success only after replacement succeeds. On failure, discard the proposed state; retain the previous file/state and return 503. Do not fall back to non-atomic copy-over. Orphan temporary files are ignored at startup; they are never authoritative. Verify replacement behavior on Windows. This addresses process/IO failure, not an unconditional guarantee against hardware/power loss.

Use one short commit queue for auth changes and post writes, plus per-username login queues spanning limit check, password verification, and commit. Heavy crypto is outside the commit queue. Registration checks uniqueness again inside commit. Posting resolves the session again inside commit so logout and post acceptance have an explicit order. No operation needs to modify both files atomically: registering/logging in/out changes auth only; publishing changes posts only.

## User

| Field | Type | Rules |
| --- | --- | --- |
| id | UUID string | Generated by server; immutable |
| username | string | Trim outer whitespace, NFC normalize; preserve English display case |
| usernameKey | string | username with ASCII A–Z folded to a–z; unique |
| password | object | Internal verifier metadata only: algorithm, N, r, p, salt, derivedKey, keyLength |
| createdAt | UTC ISO string | Server time |

Validate usernames by Unicode code points after NFC: 3–30. Each character must be an ASCII English letter, an Arabic-script Unicode letter, ASCII digit, Arabic-Indic digit U+0660–0669, Eastern Arabic digit U+06F0–06F9, or underscore. Arabic marks, punctuation, whitespace inside the name, emoji, and other scripts are rejected. Do not equate different Arabic letters (for example ا and أ) or different digit scripts. Return the normalized display name in the user response.

Passwords: 15–128 Unicode code points; preserve exact input including spaces and case, with no trimming or Unicode normalization. Reject non-string values and invalid surrogate sequences. Encode valid strings as UTF-8 for hashing. Salt: random 16 bytes; scrypt N=131072, r=8, p=1, keyLength=64 bytes, maxmem=256 MiB per call. Store salt/key as base64. Never return or log this object. Constant-time equal-length derived-key comparison; use a dummy verifier for syntactically valid unknown usernames.

Public User shape is exactly `{id,username}`. One User has many Sessions and new Posts. No update/delete/reset flows in this scope.

## Session

| Field | Type | Rules |
| --- | --- | --- |
| tokenHash | hex string | SHA-256 of 32-byte random opaque token; unique |
| userId | UUID string | References an existing user |
| createdAt | UTC ISO string | Successful login time |
| expiresAt | UTC ISO string | createdAt + 24 hours; fixed, never sliding |

Only raw token travels in the HttpOnly cookie; never persist it or send it in JSON. Every successful login generates a new token; when a current session cookie is present, revoke that session in the same auth snapshot. Other devices remain signed in. A session is valid only when its user exists and now < expiresAt. Logout removes it before responding; expired sessions may be removed lazily without changing the validity rule. Persistent sessions remain usable after restart until expiry/revocation.

Transitions: absent → active on login; active → absent on logout or replacement; active → expired when now >= expiresAt. Clearing a cookie alone is not revocation.

## LoginAttemptWindow

| Field | Type | Rules |
| --- | --- | --- |
| usernameKey | string | Normalized key; no account relationship required |
| failures | UTC timestamp array | Failed verifications strictly within preceding 15 minutes |
| blockedUntil | UTC timestamp or null | Time of fifth failure + 15 minutes |

At attempt time prune failures at or before now minus 15 minutes. While now < blockedUntil reject without password verification; blocked attempts do not extend the deadline. On the fifth failure persist the block but return the normal 401; the sixth/subsequent attempts return 429. At now >= blockedUntil clear the record and permit a fresh attempt. Success clears failures. Unknown names follow identical state transitions and dummy hashing; malformed requests fail validation without recording a credential failure. Serialize attempts by key so concurrent requests cannot bypass the threshold. Persist changes, including successful reset, before responding. Expired records are pruned during startup and mutations. Never log password, token, or entire request bodies.

## Post compatibility

Existing fields remain `id:number,name:string,text:string,created_at:UTC ISO string`. New posts additionally store `userId:UUID` and derive `name` from the session user. Older records lacking userId remain unchanged; never backfill by matching names. Public responses retain the four existing fields and expose `userId:null` for legacy records without rewriting them. New IDs keep the existing monotonically increasing integer behavior under the commit queue. Text remains required and trimmed, with a 2000-code-point maximum matching the existing composer intention.

## Test seams

Inject storage directory, clock, and controllable write failure into an app factory while preserving the default server entry point/export. Tests use temporary directories and real HTTP on ephemeral ports; time manipulation is available only through injected test dependencies, never a public endpoint. Production crypto profile must be exercised by integration and load tests.
